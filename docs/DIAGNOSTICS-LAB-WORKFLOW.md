# Diagnostics: laboratory orders and reports

This increment provides an identified-specimen workflow and a review/release boundary, with a clinician worklist and patient result view. It uses the existing Diagnostics service, Staff Web and Flutter app. It is not an accreditation claim or a complete laboratory information system.

## Workflow

1. An active verified clinician involved in the care thread chooses the investigation and priority. An optional consultation must belong to the same patient and care thread and cannot be cancelled. The web form requires an explicit test choice and, for laboratory work, an explicit staffed destination or clinician-managed choice. Other approved test names/codes can be entered; the available examples are not a validated laboratory test catalogue. An order and its required audit entry commit together.
2. Assigned laboratory staff check the patient/order against the specimen label and record its reference, type and collection time when known. The server records receipt time and staff identity separately. Collection time is never invented from receipt time. Legacy clients may omit specimen metadata; historical missing fields display as not recorded.
3. Staff enter results, units, applicable reference/critical bounds and comments. Saving from the laboratory workspace creates a **preliminary** report. It remains `collected` in the existing lifecycle, with `report_state=preliminary` and preparation metadata. Patients receive no preliminary values, narrative, attachment or critical flag. Authorized staff can inspect the preliminary report, clearly labelled as unreleased.
4. Preliminary corrections require the current version. Each replaced set of values, comments and original preparation identity/time is archived transactionally in `investigation_report_revisions`, together with the correcting actor and order version. This history has no patient-facing read endpoint. Correction, current values, version and audit are one transaction.
5. A currently assigned laboratory staff member reviews the report and explicitly authorizes release. The server checks facility membership and version and records release identity, name and time. The final report becomes visible to the patient and ordering clinician. Concurrent release has one winner. Final results cannot be overwritten or corrected through the preliminary workflow.
6. The ordering clinician explicitly acknowledges a final report, using its displayed version. Opening or printing it does not acknowledge receipt. A critical filter shows released, unacknowledged critical findings and removes them after acknowledgement.

## Worklists and reporting

The clinician worklist supports server-side search by patient name, test, specimen reference or exact order UUID, before cursor pagination. Filters distinguish awaiting specimen, in-laboratory work, final reports awaiting review and acknowledged reports. Critical flags and clinical priority are separate. Loaded counts are not hospital-wide totals. The lab queue shows specimen reference and preliminary/final status.

The printable final report contains patient/order identifiers, laboratory, requesting clinician, specimen details, collection/receipt/release times, release authorizer, results, units, reference intervals, flags, comments and clinician acknowledgement time. Report times include year and time zone. Print styling hides navigation and actions. The patient app displays the same released findings in a layout suitable for narrow screens and enlarged text, with clear error/retry states. Account changes clear current data and invalidate delayed reads; web report/worklist boundaries check their owning session. Referral and emergency work remain separate.

Bounds are supplied for the individual report; no clinical thresholds or population intervals are invented. Numeric critical flags are computed by the service. Qualitative/non-finite values and values with no applicable bounds return `not_assessed` instead of being presented as normal. Critical bounds are retained with the result. This is not automated qualitative interpretation, diagnostic advice or proof that a clinician has been contacted. The UI directs staff to the facility's urgent communication process. No new automatic SMS/pager escalation, response SLA or critical-result read-back protocol is claimed.

## Compatibility and deployment

The new web laboratory path uses `POST /results` with `save_as_draft=true`, then `POST /release` with the current `base_version` and `confirm_review=true`. Preliminary corrections use the same draft endpoint. `/collect` accepts specimen metadata; `/acknowledge` accepts an optional version. Existing direct final submissions remain supported when `save_as_draft` is omitted. Consequently the review boundary is the default updated UI workflow, not an enforced independent dual-signature policy across all legacy integrations.

Deploy the additive migrations `20261112170000_diagnostics_reporting` and `20261112173000_diagnostics_preliminary_revisions` before the service/app update and regenerate Prisma. They were applied only to the owned local development database after private backups; production was not changed. They do not invent provenance for old results. Review access, retention and approved laboratory procedures before real use. NextAuth login/refresh fetches explicitly disable caching so new logins cannot reuse cached token responses.

Remaining capabilities outside this increment include a governed test catalogue, specimen rejection/recollection, analyzer interfaces, barcode hardware, formal quality-control validation, independent approver privileges, final-report amendments with authorized redistribution, cryptographic signatures and a verified critical-result contact/read-back process. Released-report errors require the facility's governed amendment process; do not change them directly in the database.

## Verification

The database suite runs against an ephemeral loopback-only `ahealth_test` PostgreSQL cluster with all migrations, never the running development/production database. It covers ownership, current staff eligibility, laboratory membership/revocation, specimen receipt, concurrent filing, patient redaction, critical bounds, preliminary correction history, release races, versioned acknowledgement and query filters. Flutter coverage includes API error recovery, release visibility, identity changes and enlarged-text layout. Firefox acceptance uses real local synthetic clinician/lab logins and real Diagnostics HTTP requests through the BFF; it creates its own synthetic order and exercises specimen receipt, preliminary preparation/correction, release, printing layout and clinician acknowledgement. Test records are synthetic; no real specimen or analyzer was used.

The workflow draws on WHO's guidance on [result reporting and records](https://extranet.who.int/lqsi/content/write-sop-recording-reporting-and-archiving-results) and [laboratory information management](https://extranet.who.int/lqsi/checklist/2/14), particularly traceable authorization, clear corrections and secure records. Local clinical governance and accreditation assessment are separate from this implementation.
